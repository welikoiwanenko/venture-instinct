# Venture Instinct

Продуктове бачення та специфікація PoC 0.1 — редакція 2, 22 вересня 2026.

**Статус:** робочий дизайн для реалізації та перевірки. Документ враховує ревʼю R01–R33. Ревʼю та попередня редакція зберігаються поза репозиторієм як історичні джерела.

Ця редакція задає конкретні правила PoC. Числові значення є початковою конфігурацією, яку потрібно калібрувати на тестах; вони не є результатами проведеного playtest. Vision 1.0 описує напрям розвитку й не входить автоматично в обсяг 0.1.

## 1. Як читати документ

Використовуються чотири статуси:

| Статус | Значення |
|---|---|
| **Рішення 0.1** | Робоче правило цієї редакції; реалізація має йому відповідати до явної зміни дизайну |
| **Гіпотеза** | Параметр або очікування, які треба перевірити; стартове значення задане |
| **Vision 1.0** | Майбутня система, яку PoC не зобовʼязаний реалізовувати |
| **Відкладено** | Свідомо виключено з поточної версії |

У розділах 4–19 правила без окремої позначки мають статус «Рішення 0.1». Таблиця конфігурації в §5 містить гіпотези балансу. Зміна цих параметрів створює нову версію конфігурації кампанії; активна кампанія використовує свою зафіксовану версію.

| Термін | Визначення |
|---|---|
| Week / тиждень | Атомарний крок симуляції; календар рухається тільки при завершенні тижня |
| Слот | Одиниця робочого часу персонажа; читання відомих матеріалів не витрачає слотів |
| Команда | Прийнятий системою намір гравця: змінити рішення, завершити тиждень із планом тощо |
| Подія | Факт, який уже відбувся у світі й може мати причинні звʼязки з іншими фактами |
| Спостереження | Отримане персонажем свідчення: лист, метрика, відповідь, новина; може бути неповним або хибним |
| Hidden state | Фактичний внутрішній стан світу, недоступний напряму гравцю |
| Lead | Відома гравцю компанія або засновник, щодо яких можна продовжити пошук |
| Opportunity | Конкретна доступна інвестиційна пропозиція з умовами та дедлайном |
| Run | Одна кампанія PoC від початкового стану до підсумку |
| Replay | Повторне обчислення кампанії з початкових даних та журналу прийнятих команд |

## 2. Продукт і бажаний досвід

Venture Instinct — покроковий narrative management simulator про пошук стартапів, інвестиції та людей, які будують компанії.

Гравець знаходить неоднозначні сигнали, перевіряє власні припущення, обирає, кому довірити капітал, і спостерігає за наслідками протягом років. Компанії не є одноразовими картками. Їхні засновники памʼятають важливі контакти, приймають власні рішення, іноді відмовляються від допомоги та змінюються після невдач.

Основні переживання:

- «Я помітив їх раніше за інших і зрозумів, що варто перевірити».
- «Мені подобається команда, але я не впевнений у її бізнесі».
- «Я допоміг у конкретний момент, проте результат не був повністю під моїм контролем».
- «Моя теза підтвердилась» або «я неправильно витлумачив доступні свідчення».
- «Я відхилив їх з обґрунтованих причин, але майбутнє склалося інакше».

**Основна аудиторія — гіпотеза:** гравці, яким подобаються стратегічні рішення через документи, персонажі та обмежені ресурси. Досвід роботи з інвестиціями не потрібен. PoC перевіряє доступність для людей як зі знанням стартапів, так і без нього.

**Платформа:** локальний desktop-продукт; Steam — орієнтир для 1.0. PoC запускається офлайн через TUI. Основна мова першого тестового контенту — українська; ідентифікатори та технічні назви — англійські. Вибір мов комерційного релізу відкладено.

## 3. Незмінні принципи дизайну

1. **Оцінювати людей і докази.** Немає видимого або внутрішнього універсального `startup quality`, який визначає переможця. Є кілька причинно значущих характеристик із різними компромісами.
2. **Неповна інформація.** Інтерфейс показує отримані свідчення, їхні джерела й дати. Додаткове дослідження зменшує окрему невизначеність, але не відкриває всю правду.
3. **Обмежена увага.** Придбання нової інформації та допомога коштують робочого часу. Читання, порівняння та обдумування вже відомого безкоштовні.
4. **Автономія компаній.** Гравець пропонує ресурси й допомогу; founders вирішують, як ними скористатися. Інвестиція має реальний вплив на гроші та можливості компанії.
5. **Довга памʼять.** Історія discovery, ранні докази, рішення та важливі взаємодії зберігаються. Нові відомості не переписують старі листи.
6. **Невдача нормальна.** Фінансовий результат і обґрунтованість рішення оцінюються окремо. Успіх після PASS не доводить, що гравець мав передбачити його.
7. **Тижнева симуляція, гнучка частота взаємодії.** Усі роки обробляються тижнями; тихі періоди можна проходити автоматично.
8. **Прогресія скорочує обовʼязкову рутину.** Більший масштаб має змінювати тип рішень. Нову систему не додають лише тому, що попередня виявилася нецікавою.

Для оцінки функцій ставимо питання: чи допомагає вона цікаво знайти компанію, осмислено вирішити щодо інвестиції або захотіти дізнатися її подальшу долю? Для організаційного шару додається: чи цікаво встановити правила роботи команди й оцінити їхні наслідки?

## 4. Що саме перевіряє PoC

Гравець — інвестор із делегованим мандатом на невеликий бюджет у вже наявному фонді. Він сам приймає рішення в межах мандата. Карʼєрний рівень, схвалення керівника, особисті фінанси та залучення грошей фонду в PoC не симулюються.

PoC перевіряє три окремі гіпотези:

| Гіпотеза | Очікувана поведінка |
|---|---|
| H1: оцінювання цікаве | Гравець зіставляє суперечливі свідчення, обирає перевірку й пояснює компроміс |
| H2: outbound відчувається власним відкриттям | Гравець памʼятає початковий сигнал та обраний ним напрям пошуку |
| H3: доля портфеля цікава після інвестиції | Гравець повертається до конкретних компаній, реагує на їхні потреби й хоче побачити наслідки |

PoC не доводить, що гра працюватиме десятки годин, що tycoon буде цікавим або що знайдено ринковий попит.

**Обовʼязковий scope 0.1:** inbound і два джерела outbound; дослідження; outreach; інтервʼю з вибором питань; інвестиції на фіксованих початкових умовах; причинна тижнева симуляція; три типи підтримки; життя відхилених компаній; дедлайни; fast advance; фінал; локальне збереження; replay; TUI та внутрішній MCP із розділеними playtest/debug доступами.

**Відкладено:** карʼєру, власну фірму, найм, делегування, travel, конференції, міста, повноцінну конкуренцію фондів, переговори про початкові terms, повторні інвестиції гравця, складні фінансові інструменти, vector search, runtime-LLM, графічний UI, Steam, акаунти, мережевий backend. Наявність локального simulation engine та MCP не означає мережевий сервіс.

## 5. Стартова конфігурація і темп

Усі числа в таблиці — **гіпотези балансу**. Структура правил залишається сталою під час одного тестового набору.

| Параметр | Базове значення 0.1 |
|---|---|
| Вікно нових інвестицій | Тижні 1–8 включно |
| Робочий час | 5 слотів кожного тижня; залишок не переноситься |
| Початковий інвестиційний капітал | $1 000 000 |
| Один чек | $200 000 за 10% після цієї інвестиції |
| Максимум початкових інвестицій | 5; дозволено 0–4 |
| Inbound | 20 компаній, заявки надходять двома хвилями на початку тижнів 1 і 3 |
| Outbound | 10 додаткових компаній, не відомих гравцю на старті |
| Джерела outbound | Технічні спільноти; сигнали від клієнтів та найму |
| Бізнес-моделі | B2B software із регулярними платежами; три тематичні сектори |
| Сектори | Developer tools, автоматизація бізнес-процесів, logistics software |
| Інтервʼю | Орієнтир 6–10 за run; окремого штучного ліміту немає |
| Горизонт | 156 завершених тижнів від старту, включно з фазою відбору |
| Планова тривалість | 60–90 активних хвилин; перевіряється окремо для двох фаз |
| Портфельні підсумки | Digest раз на 13 тижнів; значущі запити — за фактичними тригерами |

Річні порівняння в PoC використовують умовні 52 тижні. Гра показує `Year 1 / Week 3`, а не календарні дати, щоб не змішувати бухгалтерські періоди з календарем. Реальний календар може бути доданий пізніше.

Вісім тижнів відбору — це 40 слотів. Пʼять інвестицій, десять інтервʼю й повне дослідження всіх 30 компаній у цей бюджет не поміщаються. Гравець має визначати, де зупинити перевірку.

Початковий контентний бюджет: заявка приблизно 80–140 слів, research 60–120, інтервʼю до 250 слів загалом, звичайний update 40–90. Це верхні орієнтири редагування, а не вимога заповнити обсяг. Значущі факти доступні в короткому структурованому резюме без втрати джерела та невизначеності.

## 6. Єдина модель часу

### 6.1 Планування

На початку тижня W гравець має стан після тижня W−1, доступні спостереження, невирішені запити та 5 слотів. Він читає матеріали й складає план. Чернетку можна редагувати без витрат; вона не впливає на симуляцію та не генерує нових відомостей.

`End Week` подає весь план на перевірку та виконання. Неприпустимий план відхиляється цілком без руху часу, витрат чи споживання RNG. Інтерфейс перед виконанням показує дії, витрати, угоди та відомі дедлайни, які залишаться без відповіді.

Після прийняття плану він незмінний. Дії одного плану не можуть використовувати результати інших дій цього самого тижня. Наприклад, відповідь на outreach у тижні 3 дозволяє планувати інтервʼю не раніше тижня 4. Відкриття нової компанії під час scout не дозволяє інвестувати в неї заднім числом.

Shortlist, PASS, теги, нотатки та налаштування alerts можна змінювати між тижнями. Це журналювані рішення гравця, які не рухають світ і не дають нових свідчень. Позначка PASS у PoC не є листом засновнику й сама по собі не змінює стосунки.

### 6.2 Порядок завершення тижня

Усі фази застосовуються в одному й тому самому порядку:

1. Перевірити план за відомим станом початку W, зарезервувати слоти та інвестиційні кошти.
2. Виконати дозволені початкові угоди гравця та раніше погоджені зовнішні раунди/продажі з датою закриття W. Кошти фінансування надходять компанії перед її тижневими витратами. Продаж переводить її в `acquired`, тому операційна фаза її пропускає. Звичайний економічний shock цього тижня не скасовує вже виконану угоду. Угода не виконується для компанії, яка завершила діяльність раніше; зарезервовані, але не списані гроші звільняються.
3. Завершити належні на W відкладені дії: відповіді, interviews, research, introductions. Нова зовнішня фінансова угода, погоджена зараз, закривається не раніше W+1. Дослідження знімає свідчення зі стану після угод, але до операційної фази; їхній період явно збережений.
4. Застосувати спільні ринкові зміни, рішення founders та операційну симуляцію компаній. Обробити причинні події й переходи lifecycle.
5. Закрити невикористані opportunities із дедлайном W; виконати defaults прострочених запитів. Дедлайн включний: відповідь у прийнятому плані W встигає. Будь-який новий запит, доставлений наприкінці W, має дедлайн щонайменше W+1, незалежно від фази створення.
6. Доставити дозволені спостереження та наступні запити, зберегти стан після W і перевірити завершення кампанії.
7. Якщо кампанія триває, відкрити планування W+1 і відновити 5 слотів.

Одночасні події обробляються за явним пріоритетом і стабільним ID. Якщо effect залежить від іншої події, він має причинне посилання й виконується після неї. Уже закриті компанії не отримують звичайних операційних подій.

Якщо відкладена дія втратила сенс через зміну обставин, час, уже витрачений на її запуск, не повертається; гравець отримує пояснення. Невиконана фінансова операція не списує гроші. Планувальник не використовує невідомі гравцю обставини як прихований прогноз під час попередньої валідації.

### 6.3 Приклад

У тижні 4 гравець планує два research по 1 слоту, одне interview за 2 та scout за 1. Усі 5 слотів зайняті. Якщо він хоче витратити 2 слоти на допомогу портфельній компанії, треба прибрати частину плану. Результати досліджень зʼявляться на початку тижня 5; рішення про інвестицію на їхній основі можливе у тижні 5, якщо opportunity ще відкрита.

## 7. Дії та їхня вартість

| Дія | Слоти | Передумови | Результат |
|---|---:|---|---|
| Read / compare / search archive | 0 | Матеріал уже отриманий | Нове представлення тих самих знань |
| Shortlist / PASS / note | 0 | Відома компанія | Зміна власного рішення або запису; можна переглянути |
| Scout | 1 | Обрані джерело та пошукова гіпотеза | До 2 доступних сигналів або обґрунтована відсутність результату |
| Research | 1 | Відома компанія, доступна конкретна перевірка | Одне свідчення щодо обраного питання |
| Outreach | 1 | Є контактний шлях, немає незавершеного контакту чи cooldown | Відповідь, відтермінування, відмова або відсутність відповіді |
| Interview | 2 | Є згода та доступне вікно зустрічі | Відповіді на максимум 3 обрані питання |
| Invest | 1 | Відкрита пропозиція, бюджет, тиждень 1–8 | Чек, частка, портфельні інформаційні права |
| Customer introduction | 2 | Активний запит, відповідний невикористаний контакт | Пропозиція знайомства з потенційним клієнтом |
| Talent introduction | 2 | Активний запит і доступний профіль кандидата | Пропозиція знайомства для ключової ролі |
| Investor introduction | 2 | Активний запит і доступний контакт інвестора | Додатковий шлях до наступного раунду |
| Decline request | 0 | Відкритий запит | Явна відмова; описаний default |
| End Week | — | Валідний план | Завершення одного тижня |
| Fast Advance | — | Немає неврахованих блокуючих рішень | Послідовність звичайних тижнів за правилами §13 |

Research та scout завершуються наприкінці поточного тижня. Відповідь на outreach може надійти наприкінці цього тижня або пізніше; якщо за 2 тижні відповіді немає, спроба переходить у `no_response`. План інтервʼю містить питання до завершення тижня; уточнення після прочитання відповідей потребує нової зустрічі. Це навмисне спрощення 0.1, яке перевіряється на тесті.

Безпосередня інвестиція без інтервʼю дозволена, якщо є пропозиція. Research не є обовʼязковою формальною сходинкою перед outreach. Витрати часу оплачують нову роботу, а не дозвіл натиснути наступну кнопку.

## 8. Discovery, контакти та доступність угод

### 8.1 Inbound

Заявка містить публічний опис, бізнес-модель, імена founders, заявлені метрики з періодом, контактний шлях і, якщо надано, інвестиційні умови. Заповнена заявка не гарантує достовірності даних або згоди на угоду.

Перша хвиля дає матеріал для початку; друга створює альтернативу пізнім рішенням і не дозволяє повністю спланувати run на першому екрані. Заявки можна читати в короткому списку або розгортати. Немає автоматичного рейтингу кандидатів.

### 8.2 Outbound

Гравець спочатку обирає джерело та гіпотезу, наприклад «інструмент використовують поза командою автора» або «невелика компанія наймає людей для роботи з платними клієнтами». Scout повертає доступні у цьому джерелі свідчення. Гравець сам вирішує, яке з них перетворити на lead.

| Джерело | Перевага | Неоднозначність |
|---|---|---|
| Технічні спільноти | Ранній доступ до продуктів і технічних founders | Популярність може не перетворитися на платний попит |
| Клієнтські та hiring-сигнали | Ознаки реального використання та комерційної активності | Концентрація клієнтів, показові вакансії, ріст витрат |

Сигнали породжуються поточним світом, а не створюють майбутнього переможця під обрану категорію. У кожного є вікно доступності, походження й дата. Частина outbound-компаній ще не залишає доступних сигналів у тижнях 1–8; це налаштовується та показується в debug, без повідомлення гравцю точної кількості «прихованих скарбів».

Повторний scout тієї самої пари `джерело + гіпотеза` у тому самому тижні недоступний. У наступному тижні він може дати нові свідчення лише якщо вони існують. Перевідкриття картки не генерує нову випадковість.

### 8.3 Незалежні стани

Одна компанія має стабільний ID та кілька незалежних вимірів:

| Вимір | Стани |
|---|---|
| Відомість | unknown → signal → identified |
| Рішення гравця | undecided / shortlisted / passed / invested |
| Контакт | none / pending / deferred / no_response / declined / meeting_available |
| Opportunity | unavailable / open / committed / expired / withdrawn |
| Lifecycle компанії | operating / distressed / shutdown / acquired |

Нова згадка через інше джерело доповнює історію відомої компанії. PASS можна переглянути, якщо угода доступна й вікно інвестицій не закрите. `Ignore signal` архівує конкретне свідчення, а не назавжди відхиляє компанію.

Повторний outreach після `no_response` або тимчасового `declined` дозволений через 2 тижні; `deferred` має видиму дату повторного контакту. Не більше 2 непроханих спроб на компанію у фазі відбору; нове запрошення founder відкриває контакт повторно. Ці обмеження — початкові параметри балансу.

У PoC конкурентний тиск представлений строком пропозиції та можливістю залучити альтернативні гроші після його закінчення. Немає прихованої гонки з NPC, яка анулює пропозицію вже під час планування. Відоме скасування доставляється перед наступним планом. Кожна нова пропозиція має хоча б один повний тиждень для відповіді.

## 9. Інформація та дослідження

### 9.1 Три різні шари

**Світ** містить фактичний стан і події. **Персонажі** мають доступні їм факти, інтерпретації та наміри. **Гравець** має тільки доставлені спостереження. Narrative формує повідомлення з дозволених знань конкретного автора.

Спостереження зберігає `observation_id`, `company_id`, джерело/автора, дату отримання, період факту, заявлене значення або текст, посилання на попередні свідчення та доступний гравцю статус перевірки. Внутрішній запис додатково може містити звʼязок із реальним фактом і причину викривлення; ці поля не потрапляють у player API.

Статуси на екрані: «зі слів founder», «публічне джерело», «підтверджено цією перевіркою», «є суперечливі дані», «застарілий період». Вони не є точним відсотком достовірності. Підтвердження одного періоду не гарантує майбутній стан.

Старі матеріали незмінні. Нова цифра додається як нове свідчення; порівняння показує різницю й дати. Alerts та сортування «потребує уваги» обчислюються тільки з доступних спостережень, а не з прихованої ймовірності банкрутства.

### 9.2 Research як перевірка гіпотези

| Напрям | Приклад питання | Можливий результат |
|---|---|---|
| Якість росту | Хто повертається після першого використання? | Когортні дані за доступний період або відсутність доступу |
| Клієнти | Чи є реальні платежі та залежність від одного замовника? | Підтвердження частини контрактів, концентрація, розбіжність |
| Команда | Хто виконував ключову роботу в минулому проєкті? | Свідчення про конкретні вчинки та межі досвіду |
| Продукт | Чи користуються продуктом за заявленим сценарієм? | Ознаки іншої аудиторії або реального використання |

Доступні лише перевірки, для яких є джерело. Повтор того самого питання щодо того самого набору доказів повертає вже відомий матеріал без нової платної дії. Новий період чи джерело можуть відкрити повторну перевірку. «Не вдалося отримати дані» є допустимим результатом витраченого часу, але не універсальною ознакою обману.

### 9.3 Інтервʼю

Гравець обирає до трьох питань: походження метрики, суперечність у матеріалах, роль співзасновника, поточний ризик, план використання грошей. Список формується з відомого контексту; немає запитань, які видають hidden truth своєю назвою.

Відповідь залежить від знань, мотиву й попередньої поведінки founder. Вона може містити обґрунтоване пояснення, помилкове переконання, ухилення або чесне «не знаємо». Красномовність не дає прямого бонуса до фінансового успіху. Немає завжди правильного питання, яке відкриває переможця.

## 10. Компанії, founders і причинна симуляція

### 10.1 Межі моделі

PoC використовує спільну спрощену модель B2B software. Це ігрова абстракція, а не модель реального інвестиційного прогнозування. Сектори відрізняються параметрами продажу, продуктової роботи та ринкового впливу; принципово інші бізнес-моделі відкладено.

Компанії створюються з авторських профілів і контрольованих варіацій. Профіль задає стартові умови, людей, конфлікти й доступні докази. Він не містить прапорця `winner`, наперед заданого exit або гарантованого фінального outcome.

### 10.2 Мінімальний стан

| Компонент | Дані | Причинний вплив |
|---|---|---|
| Гроші | Cash, тижневі надходження й витрати | Runway, здатність фінансувати продукт, найм і продажі |
| Клієнти | Платні клієнти, ціна, когорта/концентрація | Виручка, churn, ризик втрати великого контракту |
| Продукт | Fit для поточного сегмента, progress milestone | Конверсія, утримання, відкриття нового сценарію використання |
| Команда | Склад, спеціалізації, витрати, доступна продуктивність | Швидкість виконання та можливість реалізувати стратегію |
| Відносини founders | Узгодженість, невирішені конфлікти, зобовʼязання | Координація, затримки, ризик розходження |
| Ринок | Попит у секторі, режим доступності капіталу | Кількість leads, умови раундів, можливість продажу |
| Стратегія founder | Product / growth / conserve / fundraising / pivot | Розподіл зусиль і витрат |
| Звʼязок із гравцем | Історія взаємодії, прийняті/відхилені introductions | Доступ до співпраці та довіра до конкретної допомоги |

Грошові значення зберігаються цілими одиницями cents. Частки, імовірності й коефіцієнти — у basis points або іншому зафіксованому цілочисельному масштабі. Округлення кожної операції визначено в math-модулі; домен не залежить від форматування UI.

### 10.3 Операційний крок

Для кожного тижня обчислюється послідовність:

1. Зі стану початку операційної фази визначити стратегію founders та її витрати. Ефекти нових hires і milestones, завершених зараз, починаються з наступного тижня.
2. Визначити leads зі стартового каналу продажу, ринкового попиту, обраного бюджету росту та активних клієнтських introductions.
3. Обчислити нових клієнтів за конверсією, а втрачених — за churn і окремими подіями. Втрата не може перевищити наявну кількість. Нові клієнти цього тижня не churn-ять у тому самому кроці.
4. Оновити платних клієнтів. У базовій моделі всі активні клієнти на кінець кроку платять тижневу ціну; дебіторська заборгованість і частковий тиждень відкладені.
5. Застосувати виручку, операційні витрати, разові ефекти та завершення продуктової роботи.
6. Оцінити distressed/shutdown, нові потреби команди та доступність стратегічних переходів.

Базові співвідношення:

```text
leads = adjusted_base_leads + qualified_introduction_leads
new_customers = sample(leads, conversion_probability)
lost_customers = min(old_customers, sample(old_customers, churn_probability) + event_losses)
customers_next = old_customers + new_customers - lost_customers
revenue = customers_next × weekly_price
cash_next = cash_before_operations + revenue - operating_costs - one_off_costs
```

`cash_before_operations` уже включає фінансування, закрите в попередніх фазах тижня. `sample` використовує зафіксований доменний RNG. Fit впливає на conversion і churn; відповідна компетенція команди — на продуктовий progress; незлагодженість зменшує продуктивність; growth збільшує leads і витрати. Відсутність cash не замінюється випадковою подією «врятувались».

Конкретні коефіцієнти задаються версійованим набором balance data. Початковий технічний fixture: fit у межах 0–100, `conversion_bps = 200 + 15 × fit`, `churn_bps = 250 − 2 × fit`; усі ймовірності обмежуються 0–10 000. Це лише стартові значення для сценаріїв, не твердження про реальні ринки. Темпи росту, ціна, витрати й продуктивність задаються профілем компанії; сценарій без цих полів не запускається.

### 10.4 Founders та автономні рішення

Кожен founder має спеціалізацію, здатність виконувати конкретну роботу, схильність до ризику, відкритість до допомоги, особистий мотив і власні знання про компанію. Немає загального «таланту», який одночасно вирішує продукт, продажі й чесність. Демографічні ознаки та престиж біографії не визначають імовірність успіху.

Рішення приймаються за доступним founder уявленням про стан. Стартова політика, із персональними варіаціями порогів:

- Якщо компанія distressed — скоротити доступні витрати й шукати фінансування.
- Якщо оцінений runway менше 8 тижнів — пріоритет fundraising/conserve.
- Якщо fit менше 40 і є оплачуваний запас щонайменше на 4 тижні роботи — product або один доступний pivot.
- Якщо fit щонайменше 60, команда має комерційну спроможність і runway не менше 12 — розглядати growth.
- Інакше — продовжити поточний продуктовий план без автоматичного розширення штату.

Пороги — гіпотези. Політика задає напрям, а не безпомилкову оптимізацію. Помилкові оцінки founder можуть спричинити невдале рішення; narrative має показати доступні наслідки та пояснення.

Pivot триває 4 тижні, коштує ресурси, тимчасово скорочує розвиток старого продукту й змінює fit для нового сегмента після завершення. Старі клієнти та історія не зникають; їхній ризик відтоку змінюється за явно заданим правилом. Не більше одного одночасного pivot.

### 10.5 Події, випадковість і lifecycle

Подія має передумови, ефекти, джерела можливих спостережень, cooldown і причинні посилання. Сюжетна потреба в драмі не є достатньою передумовою.

| Подія | Причина | Наслідок |
|---|---|---|
| Втрата великого клієнта | Концентрація + ризик контракту/ринку | Менше клієнтів і виручки |
| Затримка продукту | Брак відповідної компетенції або конфлікт | Повільніший milestone, додаткові витрати |
| Вихід співзасновника | Накопичений нерозвʼязаний конфлікт | Зміна складу й продуктивності |
| Новий раунд | Потреба в капіталі, доступний інвестор, виконані умови | Cash і dilution; майбутній розвиток не гарантований |
| Продуктовий milestone | Накопичений progress | Зміна fit/можливостей із наступного тижня |
| Пропозиція придбання | Результати бізнесу + сумісний покупець + ринковий режим | Founder обирає прийняття за власною політикою |
| Shutdown | Два послідовні завершення тижня з відʼємним cash | Завершення операцій, нульова залишкова вартість у базовій моделі |

Перший тиждень із cash нижче нуля переводить компанію в `distressed`, створює термінове повідомлення для портфельного гравця та дає один повний тиждень до остаточного закриття. Відʼємний cash — тимчасовий дефіцит у спрощеній моделі, не доступна гравцю кредитна лінія. Вихід із дефіциту до кінця наступного тижня скидає цей лічильник.

Для shutdown/acquired операційні оновлення припиняються. Pivot, фінансування та швидкий ріст є подіями або характеристиками, а не взаємовиключними lifecycle-станами. Breakout — опис досягнутого масштабу в підсумку, не прихований стартовий тип компанії.

Ринкові shocks діють на групи компаній і можуть створювати корельовані невдачі. Компанії не отримують незалежне «щастя» лише тому, що гравець вважає портфель диверсифікованим. Зовнішні події, випадковість компанії та косметичний текст використовують окремі ключі RNG (§18).

## 11. Інвестиції та фінансовий результат

### 11.1 Початкові угоди

Кожна початкова угода PoC — $200 000 за 10% компанії після надходження грошей. Умовна оцінка до інвестиції — $1,8 млн, після — $2 млн. Це стандартизована ігрова умова для порівняння відбору, а не припущення про справедливу ціну різних бізнесів.

В одному run дозволено не більше 5 угод, по одній на компанію. Гравець може залишити частину або весь бюджет невикористаним. Після тижня 8 нові інвестиції гравця закриті; невикористані гроші залишаються на балансі без процентного доходу. Виплати з exit також залишаються грошима й не відкривають новий цикл відбору в PoC.

Гравець не має особистої власності в портфелі: усі показники PoC належать його інвестиційному мандату. Зарплата, бонуси, податки, fees, carry, борги й liquidation preferences відкладені. Немає follow-on, автоматичного захисту від dilution чи додаткового внеску під час кризи.

### 11.2 Наступні раунди та альтернативне фінансування

Компанії, у які гравець не вклався, також можуть знаходити гроші. Відсутність його інвестиції не означає ані гарантованого закриття, ані гарантованого фінансування іншими.

Під час fundraising founder обирає доступний зовнішній контакт. Спроба триває 3 тижні. Після завершення умови й імовірність згоди залежать від поточного стану компанії, інвестиційного мандата контакту та ринкового режиму. Introduction гравця відкриває додатковий сумісний контакт, але не гарантує угоду. Повторна спроба з тим самим інвестором потребує нової суттєвої метрики або щонайменше 8 тижнів cooldown.

Сума, pre-money оцінка, вимоги інвестора та обмеження кількості одночасних спроб задаються profile/config. Перевірка контенту відхиляє раунд без цих параметрів. Пропозиція має строк дії; founder сам приймає рішення. Укладений зовнішній раунд закривається наступного тижня. Пізніша генерація тексту не змінює його умов.

У компанії може бути лише один погоджений незакритий раунд. Прийняття альтернативного фінансування закриває несумісну початкову пропозицію й доставляє повідомлення про це до наступного планування. Нова пропозиція придбання проходить рішення founder у фазі 4 і, якщо прийнята, закривається не раніше W+1. Порядок закриття не залежить від того, через який інтерфейс гравець читає новини.

Для нового внеску F за оцінки V до раунду:

```text
нова частка попереднього власника = стара частка × V / (V + F)
частка нового інвестора = F / (V + F)
cash компанії збільшується на F
```

Усі попередні власники розмиваються пропорційно. Облік ведеться з вищою точністю, ніж відсоток на екрані; округлення залишку капіталізації має визначене правило. Сума часток після операції не перевищує 100% і не губить залишок через незалежне округлення.

### 11.3 Exit, оцінка залишку та приклад

У базовій моделі продаж дає всім власникам виплату пропорційно частці від визначеної ціни equity. Після виплати ця частка більше не входить у залишкову вартість. Shutdown дає нульове повернення; це свідоме спрощення 0.1.

Для живих компаній показується оцінка частки за останньою відомою ціною завершеного раунду, датою й позначкою «неліквідна оцінка». У 0.1 числова переоцінка відбувається лише після нового завершеного раунду або підтвердженого shutdown; негативні операційні свідчення додають позначку ризику без вигаданого точного write-down. Без нових відомостей стара оцінка стає застарілою, а не автоматично точною. Детальніша модель оцінювання відкладена.

Виконані раунди, продажі та закриття, які змінюють частку або cash мандата, автоматично створюють облікове спостереження для портфельного гравця в кінці цього тижня. Цей запис є повідомленням про операцію, а не приватним прогнозом майбутнього; він не залежить від готовності founder написати довільний update.

Приклад однієї інвестиції:

| Крок | Cash мандата | Частка | Неліквідна оцінка / виплата |
|---|---:|---:|---|
| Старт | $1 000 000 | — | — |
| Внесено $200 000 | $800 000 | 10% | Початкова оцінка частки $200 000 |
| Інший інвестор вклав $1 млн за pre-money $4 млн | $800 000 | 8% | 8% від post-money $5 млн = $400 000 |
| Компанію продано за equity value $10 млн | $1 600 000 | 0% після продажу | Отримано $800 000; залишкова оцінка цієї частки = 0 |

Після нового раунду $400 000 не зʼявляються на грошовому рахунку. Після продажу $800 000 не додаються повторно як оцінка активу.

Фінал окремо показує інвестований капітал, невикористані кошти, фактичні виплати, неліквідну оцінку та списання. Якщо інвестицій немає, кратність повернення позначається «не застосовується», без ділення на нуль. Немає єдиного hidden-truth score, який оголошує правильність усіх рішень.

## 12. Підтримка портфеля та відносини

Після першої інвестиції портфельна робота доступна паралельно з discovery. Після тижня 8 вона стає основним джерелом активних рішень. Гравець читає updates, перевіряє доступні факти й обирає, чи витрачати час та контакти на допомогу.

PoC дає невеликий фіксований набір контактів: початково 3 клієнтські, 3 talent та 3 інвесторські. Це гіпотеза балансу. Кожен контакт має видиму спеціалізацію та може бути представлений одній компанії один раз за run. Відправлене знайомство витрачає контакт навіть якщо угода не відбулася; чернетка — ні. Повноцінне розширення мережі контактів відкладено.

| Допомога | Коли доступна | Вплив | Можлива невдача |
|---|---|---|---|
| Customer introduction | Компанія шукає клієнта сумісного профілю | Після згоди founder додає обмежену кількість qualified leads на 4 тижні | Невідповідність продукту, відсутність конверсії, відмова від контакту |
| Talent introduction | Є конкретна незакрита роль | Кандидат проходить 2-тижневий процес; найм змінює компетенцію та витрати | Founder/кандидат відмовився, немає грошей на роль |
| Investor introduction | Є запит на фінансування | Відкриває додаткову fundraising-спробу за §11 | Інвестор не погодився, строк закриття занадто пізній |

Вартість кожної допомоги — 2 слоти у тижні запуску. Подальша обробка не забирає нові слоти автоматично. Параметри контакту видимі; точна ймовірність успіху — ні. Успішний hire може підвищити продуктивність і водночас скоротити runway, тому допомога не є універсальною кнопкою покращення.

Запит містить причину зі слів founder, дедлайн, дозволені відповіді та опис default. Без відповіді founder продовжує власний план; не кожна відмова карає стосунки. Відхилений introduction не змінює продуктивність магічно. Видимий follow-up повідомляє, чи відбулася зустріч і що з неї вийшло.

Повторна допомога того самого типу не накопичує ефект безмежно: один активний ефект на компанію/тип і початковий cooldown 8 тижнів після завершення. Нові запити виникають із потреб компанії, а не зі спроби заповнити календар. Якщо жодна допомога більше недоступна, запит стає повідомленням до відома з поясненням; він не блокує кожен крок.

Історія відносин зберігає конкретні події: відправлене знайомство, прийнята допомога, виконана обіцянка. Вона впливає на відкритість до співпраці, але не підміняє економіку загальним бонусом «founder likes you → success».

## 13. Fast advance та керування увагою

Fast advance виконує ті самі `End Week`, що й ручний режим. Перша ітерація може виконати явно показаний поточний план; наступні мають порожні плани. Автоматичних інвестицій, повторних introductions чи прихованого вибору відповіді немає.

Перед запуском задається цільова межа: наступний запит, наступний digest або конкретний тиждень. Після кожного кроку система перевіряє умови зупинки. Пропуск ніколи не стрибає одразу через кілька тижнів без симуляції.

| Категорія | Поведінка |
|---|---|
| Новий доступний запит із рішенням | Зупинити на першому тижні, коли гравець може відповісти |
| Відомий дедлайн shortlisted opportunity | Зупинити до завершення останнього допустимого тижня |
| Завершення інвестиційного вікна з невикористаним бюджетом | Одноразово зупинити на початку тижня 8 |
| Підтверджений critical alert портфеля | Зупинити на доставленому спостереженні |
| Обране гравцем watched company / alert | Зупинити при новому дозволеному свідченні |
| Звичайна новина, research result, reply без термінового рішення | Додати до inbox; зупинити лише за обраним правилом alerts |
| Періодичний digest | За замовчуванням зупиняти раз на 13 тижнів; можна вимкнути |
| Кінець кампанії або ручне скасування | Зупинити |

Відкритий запит можна виконати, відхилити або відкласти до обраного тижня не пізніше його дедлайну. Відкладення прибирає повторну зупинку до цієї дати, але не виконує default завчасно. Для останнього допустимого тижня доступні лише відповідь або явний вибір «залишити default». Два одночасні запити показуються разом; дефіцит слотів — змістовний вибір, а не помилка планувальника.

Зупинка не може залежати від невідомого гравцю runway або майбутнього scheduled event. Hidden crisis спершу повинна породити законне спостереження. Інтерфейс після проходження показує діапазон тижнів, причину зупинки, нові повідомлення й невирішені рішення.

Прохід виконується короткими кроками з можливістю перервати між транзакціями тижнів. Скасування не відкочує вже завершені тижні. Великий архів не повинен блокувати UI на весь прогін.

## 14. Narrative, контент і памʼять

### 14.1 Спосіб виробництва

У 0.1 використовується авторський контент із параметризованими шаблонами та умовами появи. Runtime-LLM і зовнішні запити не потрібні. Варіація тексту не змінює подію чи числа.

Кожна контентна одиниця має ID і версію, перелік допустимих фактів, автора/джерело, передумови, варіанти формулювання, cooldown та посилання на попередні події. Facts підставляються лише з дозволеного набору знань. Брехня та помилка персонажа задаються структурованою причиною, а не випадковим викривленням будь-якого числа.

Мінімальний набір першого внутрішнього зрізу: 12 компаній, 2–3 founders із помітною власною сюжетною лінією, 2 джерела discovery, щонайменше 6 сімейств причинних подій і приклади всіх трьох типів допомоги. До повного 0.1 набір розширюється до 30 компаній, зі збереженням відмінностей голосу, мотивів та початкових суперечностей.

Сімейство подій має кілька текстових варіантів, але однаковий факт не надсилається повторно лише з іншими словами. Новий update повинен додавати зміну, новий контекст, пояснення або відповідь на попереднє питання. Незмінні метрики потрапляють у digest.

### 14.2 Валідація та повторюваність

Контент перевіряється на існування згаданих персонажів і продуктів, відповідність lifecycle, періодів, одиниць виміру, ролей та джерел. У закритої компанії не зʼявляється звичайний новий клієнт. Відсутність доступного шаблону не повинна приховувати важливе рішення: є структурований fallback із дозволеними фактами.

Однаковий seed відновлює той самий світ за тієї самої версії. Новий seed змінює початкові параметри й доступні події в межах авторських профілів. Якщо профілі вже впізнаються і результат легко вгадується з назви, це провал replayability; перейменування саме по собі не вирішує проблему.

Мова текстів зберігається окремо від доменних правил. Повідомлення, уже отримані гравцем, зберігаються з текстом і версією шаблону, щоб оновлення контенту не переписувало памʼять кампанії.

### 14.3 Discovery history та інвестиційна теза

Історія компанії зберігає перший і наступні сигнали, джерела, час контактів, доступні тоді докази, PASS/shortlist, умови інвестиції та допомогу. Одне поле «source» не стирає попередні шляхи відкриття.

Перед інвестицією або PASS можна обрати до двох причин і додати коротку нотатку. Це необовʼязково. Система не приписує гравцю тезу, якої він не записав; у такому разі фінал показує лише фактичний шлях дій і доступні матеріали.

## 15. TUI та перший досвід

Основний екран показує тиждень, доступні слоти, бюджет, чергу рішень і план. Основні розділи: Inbox, Discovery, Companies, Portfolio, History, Plan. Пошук працює по отриманих текстах та відомих сутностях; vector search відкладено.

Картка компанії містить короткий опис, founders, останні отримані метрики з датами, суперечливі свідчення, відкриту opportunity, історію та доступні дії. Порівняння двох кандидатів вирівнює одиниці й періоди, але не вираховує універсальний рейтинг.

Позначки `NEEDS YOU`, `WATCH`, стан за останніми свідченнями та відповідальна особа — незалежні поля. Майбутня ознака `DELEGATED` не означатиме, що компанія здорова або не потребує уваги.

Вартість, дедлайн і час отримання результату видимі до додавання дії в план. Перед завершенням тижня є один огляд плану; читання, пошук та зміна shortlist не потребують повторних підтверджень. Невалідний вибір пояснює доступну гравцю причину, не прихований стан.

Клавіатурні команди показані на екрані; фокус і позиція читання зберігаються при поверненні. Довгі тексти мають прокручування, таблиці — компактне представлення для вузького вікна. Статуси позначаються текстом і символом, а не тільки кольором. Доступний лінійний текстовий режим для читання допоміжними засобами.

Навчальний сценарій окремий від вимірюваного run. Він показує слот, період метрики, суперечність у доказах та один наслідок дії. Термінологія пояснюється в контексті: runway, dilution, valuation. Навчання не видає універсальний рецепт відбору.

PoC повинен запускатися одним документованим локальним способом, зберігати прогрес і дозволяти продовження без налаштування зовнішніх акаунтів. Невдала навігація в TUI фіксується як UX-проблема окремо від інтересу до гри.

## 16. Завершення run та ретроспектива

Нормальне завершення — після обробки тижня 156. Живі компанії залишаються живими; exit не форсується. Запити, ефект яких лежить поза горизонтом, позначаються незавершеними. Фінальний тиждень не створює нових обовʼязкових рішень без можливості відповісти.

Після тижня 8 дозволено достроково завершити run із позначкою «оцінка на поточний тиждень». Якщо немає жодної живої портфельної компанії або інвестицій не було, гра пропонує завершення чи спостереження за відомими компаніями до горизонту. Це не автоматичний game over. Незавершена сесія, збереження й добровільний фінал — різні події телеметрії.

Підсумок має чотири частини:

1. **Гроші:** внесено, залишилося cash, отримано виплат, залишкова неліквідна оцінка з датами, списано. Фактичні гроші відокремлені від оцінок.
2. **Компанії та люди:** ключові події, прийнята допомога, зміни складу та невизначене майбутнє живих компаній.
3. **Рішення на той момент:** записана теза, доступні докази, пізніші підтвердження чи спростування. Немає автоматичного вердикту «поганий результат = дурний вибір».
4. **Discovery та відмови:** власні знахідки, обґрунтовані PASS, успішні відхилені, недосліджені та відомі, але недоступні угоди — окремі категорії.

Відомості про сторонні компанії обмежені законно отриманими новинами. Невідомі компанії не входять у «твої помилки». Якщо результат сторонньої компанії невідомий, так і написано. Debug-звіт може показати повний світ, але це окремий інструмент розробника.

Історія після PASS є тим, що фактично відбулося без інвестиції гравця. Фінал не стверджує «ти точно заробив би X», оскільки інше фінансування й інша допомога могли змінити траєкторію. Порівняння можливих альтернатив — окремий developer experiment із явно заданими втручаннями.

## 17. Архітектура, збереження та MCP

### 17.1 Компоненти

Runtime — Node.js, мова — TypeScript, локальне сховище — SQLite. Конкретні підтримувані версії runtime, драйвера й TUI-бібліотеки фіксуються при технічному bootstrap та в lockfile. Жоден із цих виборів не повинен змінювати доменні правила.

| Компонент | Відповідальність |
|---|---|
| Domain engine | Валідація команд, правила тижня, фінанси, lifecycle, RNG, причинні події |
| Observation layer | Видимість, джерела, історичні зрізи знань, доставка повідомлень |
| Narrative renderer | Текст із дозволених фактів, варіанти й локалізація |
| Persistence | Атомарні команди, state, історія, черги, snapshots, schema version |
| Application API | Єдиний набір queries/commands, revisions, errors та дозволів |
| TUI / MCP adapters | Представлення й виклики API без власних копій правил |
| Test runner | Серії кампаній, baseline-стратегії, інваріанти та метрики |

Читання даних не рухає час і не викликає доменний RNG. Будь-яка дія гравця або агента проходить ту саму валідацію. TUI не імпортує напряму hidden company state для побудови екранів.

### 17.2 Мінімальний доменний набір даних

Потрібні сутності: `campaigns`, `companies`, `founders`, `relationships`, `ownership`, `opportunities`, `contacts`, `pending_actions`, `requests`, `observations`, `commands`, `events`, `snapshots`, `player_notes`, `telemetry`.

Це логічні сутності, а не вимога мати рівно стільки таблиць. У `events` зберігаються тип, payload із конкретними змінами, week/sequence, сутність, причинні ID та версія схеми. В `commands` — ідемпотентний ID, очікувана revision, нормалізовані аргументи, результат і посилання на породжені події. Людський текст не є єдиним представленням факту.

Для resume авторитетний збережений поточний стан разом із відкладеними процесами та знаннями. Для replay авторитетні початковий manifest і прийняті команди; журнал подій використовується для звірки. Повне відновлення лише з event log не є вимогою 0.1. Snapshots — прискорення, не інше джерело істини.

### 17.3 Атомарність та життєвий цикл збереження

Прийнята команда, повʼязані списання, події, спостереження й новий state зберігаються в одній транзакції. `End Week` комітиться цілком або не комітиться. Після збою відновлюється остання завершена транзакція; відсутній частково проведений тиждень. Автозбереження відбувається після кожної прийнятої доменної команди.

Повторний запит із тим самим `command_id` повертає попередній результат. Той самий ID з іншими аргументами відхиляється. Команда зі старою `expected_revision` відхиляється без витрат; клієнт має перечитати актуальний стан. У 0.1 одна кампанія має один активний writer; адаптери не відкривають незалежні обходи цього правила.

Збереження включає незавершені outreach, раунди, introductions, дедлайни, alert acknowledgements, RNG-версію, часові лічильники, cap table та доставлені повідомлення. Чернетка плану й позиція UI можуть зберігатися окремо та не впливають на deterministic state.

При запуску перевіряються schema/simulation/content/config versions. Несумісне збереження не мігрується мовчки. Для 0.1 допустиме відновлення тією самою версією; майбутня міграція має створювати резервну копію й позначати нову гілку історії. Append-only журнал не переписується для виправлення минулого; явна корекція є новою подією або окремою developer-копією кампанії.

### 17.4 MCP Playtest та Debug

Playtest API дає ті самі матеріали й можливості, що TUI: отримати огляд, список відомих компаній, картку, матеріал, доступні дії; змінити shortlist/нотатки; подати план тижня; відповісти на запит; пройти час; зберегти й отримати підсумок.

Не допускаються hidden-поля, майбутні події, справжня достовірність повідомлень, непублічні типи помилок або список ще невідомих компаній. Пошук і pagination застосовують той самий фільтр знань. Structured JSON може бути зручніший за TUI, але не повинен містити додаткових фактів.

Debug працює через окремий capability/profile, який не додається до playtest-сесії. Він може читати повний стан, причинний журнал, стан генерації та заплановані процеси. Майбутній процес — не гарантований outcome: його передумови можуть змінитися.

Агент, який бачив debug-дані сценарію, не використовується для сліпого проходження того самого сценарію. Для developer-втручань створюється явно позначена копія, яка не змішується з чистим balance run. Debug не є доступною гравцю функцією 0.1.

## 18. Determinism, replay та технічні критерії

Manifest кампанії містить seed, початковий стан або перевірюваний generation manifest, версії simulation/content/config/RNG/math, scenario ID та хеш контентного набору. Час операційної системи, locale, порядок SQL-видачі та асинхронне завершення UI-запитів не є входами симуляції.

Випадкові вибірки адресуються стабільними ключами на кшталт `seed / stream / company_id / week / event_type / attempt_id`. Окремі streams використовуються для генерації, ринку, компаній, контактів і текстових варіантів. Послідовність додаткових читань або зайве повідомлення не зсувають результат іншої компанії. Алгоритм і порядок використання ключів версіонуються.

RNG не визначає причинність: однаковий ключ за різних станів може дати різний outcome через інші ймовірності чи передумови. Тому однаковий seed із різними інвестиціями не обіцяє тотожних майбутніх подій. Це очікувана поведінка.

Прийняті команди мають монотонний sequence. Stable IDs не створюються через wall-clock; порядок компаній і подій визначений явно. Фінансова математика й округлення не залежать від графічного форматування. На контрольних тижнях обчислюється hash доменного стану та журналу подій; телеметрія часу читання і позиція курсора в нього не входять.

Обовʼязкові технічні перевірки перед людським playtest:

| Перевірка | Очікуваний результат |
|---|---|
| Seed + manifest + ті самі команди | Тотожний доменний стан, спостереження та події |
| Збереження посеред outreach/раунду та resume | Те саме продовження без дублювання |
| Ручні кроки проти fast advance | Тотожність за однакових планів, відповідей і правил зупинки |
| TUI проти MCP | Однакові доступні факти, ціни й наслідки команд |
| Додаткові read/search/sort | Незмінний доменний стан і майбутня симуляція |
| Повтор `command_id` | Жодного повторного списання чи події |
| Збій перед commit тижня | Повністю старий або повністю новий стан |
| Дедлайн W і відповідь у плані W | Відповідь встигає; план W+1 уже запізнився |
| Два одночасні запити | Обидва видимі; слоти не перевищуються |
| Нуль інвестицій, ранній shutdown усіх | Коректний фінал без зависання та ділення на нуль |
| Раунд → dilution → exit | Гроші й частки збігаються з ручним прикладом §11 |
| Відоме хибне свідчення | Зберігається як свідчення, а не підміняє фактичний state |
| Пошук, errors та alerts у Playtest | Немає витоку hidden truth |

Інваріанти: бюджет і слоти гравця не відʼємні; жодного подвійного володіння тією самою часткою; lifecycle не воскресає без окремо описаного правила; один факт не списує ресурс двічі; подія не посилається на майбутню причину; минулі спостереження незмінні. Дозволений тимчасово відʼємний cash компанії перевіряється окремо за правилом distressed, а не загальною забороною будь-якого мінуса.

## 19. Перевірка дизайну та критерії переходу

### 19.1 Внутрішні етапи

| Етап | Scope | Що дозволено виснувати |
|---|---|---|
| A: вибір і докази | 12 компаній: 8 inbound + 4 outbound; 4 тижні відбору, бюджет $600 000, максимум 3 чеки | Чи працює конкретний цикл оцінювання |
| B: наслідки | Ті самі компанії, до 52 тижнів, 3 типи допомоги, save/load, фінал | Чи є інтерес після вибору й чи зрозуміла причинність |
| C: повний 0.1 | Конфігурація §5, MCP, replay, 156 тижнів, кілька scenario packs | Чи витримує loop заявлений обсяг і повторні проходження |

Це окремі версійовані конфігурації. У A/B швидкість sim не змінюється: один крок лишається тижнем. Для тестових fixtures допустимо підготувати стартові умови близько до важливої події, але не підміняти живу кампанію гарантованими фіналами без позначки.

### 19.2 Людський playtest

Перша хвиля повного 0.1 — 8 учасників, приблизно порівну зі знайомством із темою та без нього. Це якісний тест для пошуку проблем, не статистичне доведення попиту. Технічні збої записуються окремо; виключення сесії має задокументовану причину, а невдоволення грою не є підставою для виключення.

До запуску фіксуються build/config, протокол, критерії й однакові умови тесту. Спочатку людина проходить коротке навчання. Під час вимірюваного run модератор не підказує, кого інвестувати, і не просить дочитувати все. Наприкінці ставляться відкриті питання про запамʼятовані компанії, мотивацію інвестиції та PASS, несподівані наслідки й найменш цікаву частину.

Початкові критерії переходу до наступного етапу — **гіпотези процесу**, які фіксуються до хвилі тесту:

| Критерій | Початковий поріг для 8 учасників |
|---|---|
| H1: рішення з доказами | Щонайменше 6 можуть пояснити інвестицію або обґрунтований PASS двома конкретними свідченнями та назвати невизначеність |
| H2: власне discovery | Щонайменше 5 добровільно знаходять outbound lead і пояснюють свій вибір сигналу |
| H3: привʼязаність | Щонайменше 5 наприкінці памʼятають дві компанії та конкретні події з їхньої історії |
| H3: активний інтерес | Щонайменше 4 самостійно повертаються до деталей компанії після інвестицій; технічні повтори відкриття не враховуються |
| Повторне проходження | Щонайменше 3 починають інший scenario pack, коли всім надана однакова добровільна можливість і достатній час |
| Зрозумілість | Щонайменше 6 після навчання можуть скласти валідний тижневий план і відрізнити cash від оцінки частки без допомоги |

Дотримання порогів не скасовує серйозної якісної проблеми та не підтверджує 1.0. Недотримання спершу розбирається за причиною: правила, інформація, контент, TUI, нерелевантна аудиторія чи слабкий loop. Пороги не переписуються заднім числом; наступна перевірка використовує нову зафіксовану редакцію.

### 19.3 Нудьга, тривалість і телеметрія

Локально фіксуються відкриті матеріали, повторні повернення, прийняті плани, відомі альтернативи, доступні слоти, запуск/зупинка fast advance, тип запиту, завершення та добровільний вихід. Перерва або залишений відкритим екран не вважаються доведеним читанням. Експорт для тестування — явна локальна дія.

Аналіз окремо показує реальні хвилини, календарні тижні, кількість рішень і обсяг тексту. Не можна порівнювати «набридло на тижні 60» між сесіями без урахування кількості взаємодій.

| Спостереження | Інтерпретація, яку треба перевірити | Наступна зміна |
|---|---|---|
| Швидко проходить час, потім уважно читає наслідок | Очікування цікавої події | Зберегти fast advance |
| Пропускає пояснення і не памʼятає компаній | Перевантаження, слабкі персонажі або байдужість | Скоротити активний склад і перевірити історії |
| Довго шукає старі цифри | Проблема інформаційного дизайну | Поліпшити картку та порівняння |
| Завжди обирає найбільший growth | Може існувати домінантна метрика | Перевірити модель й інформаційну цінність research |
| Любить відбір, хоче одразу завершити після нього | Portfolio loop не працює | Переробити його до розширення scope |
| Часто зупиняється без доступного рішення | Невдале правило alerts | Змінити пріоритети та digest |

Орієнтир навантаження після інвестицій: 8–15 ситуацій із доступним вибором за повний run і 12 digest-періодів за 156 тижнів. Це ціль для перевірки фактичної щільності, не квота, яка примусово створює події. Якщо причинна симуляція її не дає, змінюються параметри або сама гіпотеза loop.

### 19.4 Автоматизований баланс

Test runner порівнює випадковий допустимий вибір, inbound-only, outbound-heavy, одну просту metric-стратегію, стратегію з research та агентів. Усі мають однаковий час, бюджет і player observations. Debug-oracle, якщо використовується, є окремою верхньою межею, а не чесним конкурентом.

Початковий обсяг — 200 стартових seeds для калібрування та окремі 200 для перевірки. Число збільшується, якщо невизначеність результатів не дозволяє порівняти стратегії. Аналізуються розподіли грошових повернень, неліквідних оцінок, survival, концентрації, кількості рішень і витрат слотів; одна середня оцінка не є достатньою.

Перевага research перевіряється на сценаріях, за якими його не налаштовували. Результати одного seed порівнюються з урахуванням різних втручань і того, що вони могли змінити компанії. Агент використовується для пошуку експлойтів, недоступних станів і домінантних стратегій; його fast-forward не є виміром людської нудьги.

Для кожного агентного запуску зберігаються модель/версія, prompt, обмеження контексту та дій, ціль і повний журнал прийнятих команд. Replay гри не потребує повторного запуску агента.

## 20. Vision 1.0: карʼєра, фонд та організація

Увесь цей розділ — **Vision 1.0**. Він визначає напрям і важливі межі, але не розширює acceptance criteria PoC.

### 20.1 Карʼєра та право на рішення

| Роль | Власне рішення гравця | Новий тип відповідальності |
|---|---|---|
| Analyst | Вибір перевірок, shortlist, рекомендація з доказами | Якість аналізу та пошук сигналів |
| Associate | Контакти, інтервʼю, частина підтримки | Стосунки й ведення процесу |
| Principal | Ведення угод і делегований бюджет за мандатом | Розподіл уваги між угодами |
| Partner | Інвестиційні рішення та правила відбору | Портфель, команда й пріоритети |
| Засновник власної фірми | Мандат, люди, капітал та організація | Життєздатність системи |

Керівник пояснює рішення доступними причинами й правилами мандата; він не прихований випадковий veto. Репутація враховує атрибутований внесок у пошук, аналіз, переконання й підтримку, а також результати з часом. Один пізній exit не є єдиною умовою раннього просування.

Відкриття власної фірми добровільне. Гравець може залишитися найманим інвестором. Розблокування залежить від ресурсів, досвіду й готовності, а не від таймера «минуло 15 годин». Початкові часові припущення попередньої редакції замінюються вимірюванням реального темпу.

### 20.2 Три окремі грошові баланси

Базова модель повної гри — керуюча компанія та фонд. Акселератор із наборами учасників є окремим майбутнім варіантом, а не взаємозамінною назвою.

| Баланс | Надходження | Витрати |
|---|---|---|
| Особистий | Зарплата, визначені бонуси/виплати | Особистий запас, внесок у запуск фірми або фонду |
| Керуюча компанія | Внесок засновника, передбачений дохід за управління | Працівники, офіс, поїздки, операційні витрати |
| Фонд | Внески інвесторів, повернення портфеля | Інвестиції, зарезервовані follow-on, визначені витрати фонду, виплати інвесторам |

Кожен перехід між балансами явний і відображений з обох боків. Кошти фонду не стають особистим доходом автоматично. Нереалізований ріст оцінки не оплачує зарплати. Правила доходу за управління та розподілу прибутку задаються окремим спрощеним договором гри; точні ставки й календар потрібно обрати перед прототипом Fund Builder.

Початкова організаційна модель може використовувати один фонд із фактично внесеним капіталом, обмеженим інвестиційним періодом і видимим резервом. Capital calls, складні класи часток та юридичні структури не потрібні для першого прототипу цього шару. Інвестори фонду мають очікування щодо мандата, звітності та строків; відмова в новому капіталі створює вибір щодо масштабу й витрат.

### 20.3 Вихід від роботодавця

Переносяться особисті гроші, професійна репутація, атрибутована історія внеску й контакти, готові підтримувати стосунки. Не переносяться автоматично гроші, частки портфеля, працівники або приватні документи роботодавця.

Старі компанії залишаються у карʼєрній історії. Подальші відомості надходять із публічних джерел або за згодою founders, а не через безстроковий доступ до внутрішнього портфеля. Уже освоєні UX-зручності не блокуються повторно. Повтор ручної роботи має бути коротким і створювати новий компроміс, а не вимагати пройти навчання знову.

Невдалий запуск фірми допускає зменшення масштабу, паузу нових інвестицій або повернення до найманої ролі. Наслідки для репутації та зобовʼязань зберігаються, але невдача не обовʼязково завершує всю карʼєру.

### 20.4 Делегування

Працівник має спеціалізацію, продуктивність, оплату, мережу контактів та характерні помилки. Гравець задає мандат, ліміти, пріоритети й правила ескалації. Делегована робота користується доступною організації інформацією; працівник не бачить hidden truth автоматично.

Рекомендація містить аргументи та джерела. Для оцінки роботи доступні невелика вибірка відхилених кандидатів, повнота аргументів і довша історія рішень. Перечитування всіх заявок не є обовʼязковою умовою контролю. Одна невдала компанія не доводить некомпетентність працівника.

Задача має одного відповідального. Ручне перебирання скасовує ще не виконану делеговану дію або чекає її завершення; подвійні інвестиції та подвійні витрати заборонені. `Health`, `urgency` і `owner` — незалежні виміри.

Перші потрібні ролі — scouting/screening та portfolio support. CFO, COO, Investment Director, Head of Talent і Community додаються, коли зʼявляється конкретний обсяг відповідної роботи. Назва посади не є окремою механікою без власного рішення.

### 20.5 Різні стилі гри та travel

Особисті інтервʼю й discovery можуть залишатися доступними в late game, але гравець приймає їхню альтернативну вартість. Делегування повинно дозволяти завершувати кампанію без ручного перечитування всього потоку. Окремий прискорений старт для любителя tycoon перевіряється до обіцянки багатогодинного обовʼязкового вступу.

Travel витрачає тижневі слоти та операційні гроші. Поїздка відкриває спостереження, які не дає дистанційна розмова, але вони також неоднозначні. Порожній офіс не є автоматичним сигналом провалу. Поєднання кількох зустрічей створює логістичний вибір; детальна географія додається лише після перевірки його цінності.

### 20.6 Завершення карʼєри та late game

Гравець може добровільно завершити карʼєру й отримати підсумок внеску, людей, створеної організації та грошей. Після цього можливий sandbox, якщо він потрібен гравцю. Орієнтири late game: вибір мандата, межі зростання, нова спеціалізація, довіра до керівників і наступництво.

Якщо організація працює без щотижневого втручання, це може бути успішним фіналом. Дизайн не повинен штучно створювати нескінченні кризи, щоб заборонити гравцю завершити історію.

## 21. Порядок реалізації та Definition of Done

| Крок | Результат | Умова переходу |
|---|---|---|
| 1 | Domain skeleton, конфігурація, правила тижня, гроші та manifest | Приклад §6 і фінансовий приклад §11 відтворюються без UI |
| 2 | Knowledge model, 12 авторських компаній, discovery/research/interview | Є реальний вибір між перевірками, жодного hidden quality verdict |
| 3 | Мінімальний TUI та зріз A | Новий гравець може пройти відбір без підказок оператора |
| 4 | Причинна симуляція, підтримка, fast advance, save/load, зріз B | Наслідки відповідають правилам, збереження й дедлайни надійні |
| 5 | Повний контентний набір, MCP adapters, replay, автоматичні стратегії | Технічні критерії §18 виконані на кількох сценаріях |
| 6 | Людський playtest повного C та звіт за §19 | Задокументовано рішення continue / revise / stop для кожної гіпотези |

PoC **технічно завершений**, коли весь flow доступний людині через TUI та агенту через Playtest MCP, працюють збереження, фінал і replay, а технічні критерії пройдено. Відсутність коду в поточному документі не означає, що ці перевірки вже виконані.

PoC **продуктово перевірений**, коли проведено узгоджений playtest, зібрано контекстні дані та прийнято рішення щодо H1–H3. Негативний результат є допустимим завершенням експерименту. Він не приховується додаванням нових систем.

## 22. Реєстр припущень та відкритих рішень

| Питання | Поточне рішення / наступний крок | Статус |
|---|---|---|
| Чи працює довга прихильність без прямого контролю? | Перевірити H3 на зрізі B і повному C | Гіпотеза |
| Чи вистачає 8 тижнів і 5 слотів? | Порівняти витрати та неприйняті можливості; змінювати конфігурацію між хвилями | Гіпотеза |
| Чи вміщується run у 60–90 хвилин? | Заміряти фази та обсяг читання; за потреби скоротити pool або прийняти довший формат | Гіпотеза |
| Чи достатньо обраних питань без діалогових follow-up у тому самому тижні? | Тест зрозумілості й цікавості interview | Гіпотеза |
| Чи достатньо 3 контактів кожного типу? | Перевірити дефіцит і тривалі періоди без доступних рішень | Гіпотеза |
| Чи відповідає 156 тижнів бажаному емоційному результату? | Порівняти цікавість живих незавершених історій із фіналами | Гіпотеза |
| Який точний контент усіх 30 компаній? | Окремий версійований scenario pack за schema §10/14 до зрізу C | Відкрита авторська робота |
| Які коефіцієнти growth, витрат, rounds та exits? | Заповнити й калібрувати profile/config; fixtures перевірити до людського тесту | Відкрита балансувальна робота |
| Які runtime/бібліотеки та цільові OS PoC? | Node.js 24 LTS (≥ 24.12) запускає TypeScript напряму, без build step; зафіксовано в bootstrap (VI-6), `package.json` і `.nvmrc`. Перевіряється на macOS (розробка) і Linux (CI). Бібліотеку TUI обирає окреме завдання | Рішення 0.1 (закрито) |
| Яка економіка управління фондом у 1.0? | Окремий прототип трьох балансів і простого договору | Vision 1.0 |
| Чи потрібні LLM або semantic search? | Немає залежності в 0.1; повертатися лише за доведеної потреби | Відкладено |

Ці відкриті роботи не дозволяють реалізації довільно змінювати контракт часу, інформації чи фінансів. Нове правило фіксується в наступній редакції та отримує приклад і перевірку.
